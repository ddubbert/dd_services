# Security

How authentication, authorization and the signed file links work, what
protects the infrastructure, and what is missing. Reconstructed from the code
in 2026; open problems are numbered in [known-issues.md](known-issues.md)
and referenced here as (#n).

## Passwords and identities

dd_services stores **no passwords**.

- **Guests** have no credentials at all. Whoever holds a guest's tokens *is*
  that guest; losing the tokens means losing the account.
- **Permanent users** authenticate at **Keycloak** (OpenID Connect). The
  users service never sees the password: it receives a Keycloak access token
  in `createOrLoginUser`, validates it by calling Keycloak's `userinfo`
  endpoint, and maps the Keycloak subject id (`authId`) to its own user.

After that, all services work only with dd_services' own tokens. A Keycloak
token is accepted only by the users service.

## Tokens

| | Access token | Refresh token |
|---|---|---|
| Format | JWT, RS256 | JWT, RS256 |
| Content | `userId`, `nickname`, `isPermanent` | `userId`, random `refreshKey` |
| Lifetime | 15 min (`ACCESS_TOKEN_TTL`) | 60 min (`REFRESH_TOKEN_TTL`) |
| Signed with | access key pair | separate refresh key pair |
| Verified by | every service (public key) | users service only |

- `start.sh` generates both key pairs (RSA 4096) with passphrase-protected
  private keys (`ACCESS_KEY_PASSPHRASE`, `REFRESH_KEY_PASSPHRASE`) and copies
  only the access **public** key to sessions, files and subscriptions. Only
  the users service can issue tokens.
- **Refresh rotation:** the users service stores one `refreshKey` per user.
  Every login or refresh replaces it, so older refresh tokens stop working.
- **No revocation of access tokens:** other services verify access tokens
  offline, so a token stays valid until it expires, even after the user is
  deleted. Only the users service additionally checks that the user exists.
- Tokens travel in the `Authorization: Bearer` header (HTTP) or the
  `Authorization` connection parameter (WebSocket).

## Authorization

Every service checks permissions itself, using the `userId` from the access
token. There is no central policy and no roles beyond the session roles.

| Resource | Rule |
|---|---|
| User | `email`, `sessions`, `files` only for the user themself; `deleteUser` only for yourself |
| Session: read, prolong, add participants, leave | any member (owner or participant) |
| Session: rename, add owners, remove users, delete, link child sessions | owners only |
| Session: join as participant | anyone who knows the public session `id` |
| Session: join as owner | anyone who knows the private `adminId` (only shown to owners) |
| Session lifetime | guests may only choose `SHORT`/`X_SHORT` |
| File: read, copy, attach to another session | owner, or member of a session the file is in |
| File: delete | owner or uploader |
| Personal upload (no session) | permanent users only |
| Live updates of a session | members only |

The files and subscriptions services do not ask the sessions service; they
keep their own copy of session membership, filled from Kafka events. That
copy can lag behind, and an unknown session currently counts as allowed
(#1). Several checks are missing or weak (#2, #4, #5, #8).

## Signed file links

File contents are never sent through GraphQL. The files service hands out
**signed URLs** for its REST server, created with the
[`signed`](https://www.npmjs.com/package/signed) library and an HMAC secret
in `files/signing.pem` (random, generated by `start.sh`). Every request to a
link **also** needs a valid access token; the link alone is not enough.

| Link | From | Bound to user | Expires | Extra protection |
|---|---|---|---|---|
| Upload `POST /uploads/<sessionId>?files=…` | `getSignedFileUploadLink` | yes | 15 min (`UPLOAD_LINK_TTL`) | method POST; the allowed files (name, mimetype, size) are encrypted into the URL with AES-256-CBC, so the client cannot change them |
| Zip download `GET /files?fileId=…&fileId=…` | `getDownloadLinkForFilesOfSession`, `getDownloadLinkForFilesOfUser` | yes | 15 min | method GET |
| Single download `GET /files?fileId=…` | `File.downloadLink` | no | never (#6) | method GET |

"Bound to user" means the signature contains the user id, and the server
checks it against the id in the access token of the request. So a forwarded
upload or zip link is useless to anyone else.

On upload the server additionally checks:

- the mimetype against a whitelist (`text/*`, `image/*`, `audio/*`,
  `application/pdf`); the type is the one the client declares, the content
  is not inspected;
- name, mimetype and size (±1 %) against the encrypted list;
- at most 12 files of at most 10 MB each.

Uploaded files are stored under random UUIDs, never under the client's file
name, so a file name cannot be used for path tricks. The quota check is
currently ineffective (#3), and the encryption key and IV change with every
restart (#7).

## Abuse protection

- **Rate limiting** per user on every GraphQL operation
  (`graphql-rate-limit-directive`, counters in Redis): 60–150 requests per
  minute, 1000 for `createOrLoginUser`.
- **Depth limiting:** nested federated fields (session → files → sessions …)
  are cut off at depth 5 (`MAX_DEPTH`).
- Apollo's **CSRF prevention** is on for all GraphQL servers.
- Guests and sessions **expire** automatically (MongoDB TTL indexes), which
  limits how much abandoned data piles up.

## Infrastructure

- **Network:** Docker networks separate the parts; only the gateway, the
  files REST server and the subscriptions service publish ports. The
  users, sessions and files GraphQL servers, MongoDB, Kafka and Redis are
  only reachable inside Docker.
- **Service-to-service:** a shared static secret (`GATEWAY_BEARER_TOKEN`)
  lets a caller act as the user `gateway`. The gateway itself only forwards
  the client's token; its introspection token falls back to a hard-coded
  value (#22).
- **MongoDB:** replica set with `--auth`, one database user per service, and
  a keyfile (generated by `start.sh`) for replica authentication.
- **Redis:** password (`CACHE_PASSWORD`).
- **Kafka:** no authentication and no TLS (plaintext listeners); it relies
  on the Docker network only.
- **Secrets** come from `.env` and generated files that are git-ignored;
  `.env.example` lists them with placeholders.

## Not implemented

- **TLS:** every URL the services build is `http://`. A deployment would
  need a TLS-terminating reverse proxy in front.
- **CORS** allows every origin on all servers.
- No revocation list for access tokens, no logout endpoint.
- No audit log; some services log too much instead (#20).
- No content scanning of uploads (malware, real file type).
